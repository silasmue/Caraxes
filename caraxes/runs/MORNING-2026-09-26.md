- **Still open:**
  - **Streaming cap and cursor lag: cause found at 02:15, fix built, GPU test queued.** The
    per-frame timeline (kick, flip latch, vblank, next kick; `caraxes/tools/display-pace.py`)
    shows the display model on time: tick period 16.666 ms, 2212 of 2294 flips latch at the first
    tick after their kick, none late. The frame is lost between the latch and the guest's next
    kick: 20 to 22 ms without a client, 33 to 54 ms while streaming, where 60 Hz needs under 15.
    Right before each kick the compositor's commit does about 23 BAR2 flush reads (`R bar3
    0x00fea000`) and 2 MMU invalidates, and every trapped flush read ran a full BAR2 memfd sync
    (mean 174 us, 377327 syncs = 65.6 s per session, about 317/s), 7 to 13 ms per frame. Fix
    (branch `worktree-agent-af3f69b70fa0e2e7a`, 02c0a625, binary `-flippace-02c0a625`): a flush
    read only marks the sync as owed; the next hand-over (MMU invalidate, GSP or channel doorbell)
    or a 1 ms clock settles it; knob `CARAXES_BAR2_MEMFD_DEFER_FLUSH=0` restores the old path for
    the A/B. Expected: pre-kick run 1.5 to 3 ms, no-client cursor at 55+ kicks/s. While streaming
    the rest of the gap is Sunshine's serial per-frame chain (EGL import, CUDA, NVENC, map and
    unmap), so the cap may stay below 45 kicks/s until the scanout import cache from
    `sottr-stage.md` §11 lands. Docs: `docs/caraxes/display-pacing.md` in that worktree; the A/B
    lands in `vm4-615-flippace/NOTES.md`. Earlier attribution to Sunshine's capture pacing
    ([vm4-615-latency](nvenc-2026-09-25/vm4-615-latency/NOTES.md)) is superseded.
    **A/B verdict (03:14, [vm4-615-flippace](nvenc-2026-09-25/vm4-615-flippace/NOTES.md)):**
    the no-client display is fixed at 60 Hz (59.6 kicks/s in both deferred cells, 99 to 100 %

    **Regression, so not merged as default:** with the deferral, new GPU work while streaming
    fails 0 of 4 (vkcube aborts in device creation, glmark2 renders nothing); the same binary
    with `CARAXES_BAR2_MEMFD_DEFER_FLUSH=0` 1 of 1, the synchronous build 6 of 6. That abort is

  - Guest CPU: the trap leaders are the usermode TIME reads 0xbb0080/84 (640 to 760/s), the BAR2
    flush read (310 to 710/s) and the MMU-invalidate triple. Zero-trap work for these is next.
    Interrupt page off soft-locks the 615 guest (bug, not a tuning knob).
  - **CUDA x Vulkan, the SotTR "signal 6": cause found at 04:20, a device bug.** The c5c0
    status 0x57 is only the Vulkan driver's error path: it had waited about 11 s in user mode
    (state R, no ioctl) for the GPU's completion notifiers of its new GR channel's first
    submission, given up, unbound and freed the channel, and then allocated on the stale handle.
    The first submission never ran because **the device took the channel's first doorbell for
    another channel**: a new guest channel rings its own token (its ChID, runlist 0, e.g. 0x36 for
    chid 54), and `ctrl.rs doorbell()` looks a raw value up as a *host* token first
    (`Mirror::chid_of_host_token`); once an older mirrored channel (CUDA's, Sunshine's) holds host
    chid 54, the ring goes there. All three captures match (chid 54 / 0x36 owned by guest chid 12;
    r2: chid 48 / 0x30 by guest chid 5; the first capture: chid 50 / 0x32 by guest chid 2). It is
    per channel, which is why the async-compute sibling worked, and it grows with the number of
    mirrored channels, which is why streaming and the flush deferral made it worse. The control
    `0xd01` is NV0000_CTRL_CMD_CLIENT_GET_ADDR_SPACE_TYPE, a plain handle lookup. The host
    VA-alloc bursts come 14 s later at the client's teardown and are a separate item. Fix (in
    work, agent): resolve a raw token as a guest channel first when a guest channel with that
    ChID exists (on a collision the host token's owner is rung too, a spurious doorbell being
    harmless), and write a pool token into every mirrored channel's work-submit notifier at
    scheduling so raw host tokens never reach the guest. Built at 04:15 on branch
    `tokenfix-2026-09-26` (d1084c0a, unit tests for the collision, the no-pool path and the
    scheduling hand-out; check green; new exit line counts avoided collisions); GPU test per
    `vm4-615-tokenfix/PLAN.md` next. Also found: the global context buffers' PA is stored under the
    first channel's key and dropped with it (`channel.rs`); a per-GPU store fixes that.
    [vm4-615-cuda-vulkan](nvenc-2026-09-25/vm4-615-cuda-vulkan/NOTES.md), merged.
  - **Host VA-alloc bursts (the "VA Space alloc failed" lines): cause found at 05:05, a device
    bug with a latent isolation risk.** A Vulkan client's VA space is allocated by one client and
    dup'ed into two others; the GR channels live in the last one. At teardown the guest frees the
    owner client first, and the device's registry (`channel.rs record_free`) drops the VA space
    and its root although the alias still points to it. From then on that root has no set-B
    exclusions, so the next BAR1-pool resync tries to map the guest's kernel-RM buffers at
    0x1200xxxxx with fixed-address `NV50_MEMORY_VIRTUAL` objects (`shadow.rs`) where the host's GR
    contexts of still-live host TSGs sit: 9 regions refused, 31 host lines per teardown. Same
    collision the exclusion-release fix removed for single clients, reached through a path it
    does not cover; each guest root has its own host VA space, so no cross-process collision, and
    no stale mapping. Nothing breaks in this workload (the refused leaves are set B, never meant to
    be mirrored; host Xid 0), but a new GR channel built on such a root would mirror set A over the
    host's context VAs, the Xid 31 case. Fix built at 05:15 on branch `vaalloc-2026-09-26`
    (30a92496): a dup'ed VA space stays alive on the first surviving alias when its owner is
    freed (`rehome_duplicated_vas` in `channel.rs`, trace note on the FREE line, pool re-sync
    notes with set-B changes now reach the trace); two unit tests, 420 tests and the check green;
    binary `-vasdup-30a92496`; GPU cell (e) in `vm4-615-tokenfix/PLAN.md` (the multi-client loop,
    5 iterations, pass = no host VA-alloc line, no refused object, 0 map-failed, host Xid 0).
    [va-alloc-bursts-2026-09-26.md](../../docs/research/va-alloc-bursts-2026-09-26.md) (branch
    `vaalloc-2026-09-26`).
  - **Concurrency matrix (03:27 to 03:59, binary invhold-3bad9810, `vm4-615-concurrency/`):**
