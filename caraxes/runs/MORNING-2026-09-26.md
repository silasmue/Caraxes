## Windows (QEMU 11.1 `vfio-user-pci`, driver 617.14, `caraxes/runs/win11-2026-09-25/`)

- **State:** the driver boots the GSP-RM path, exchanges ~500 RPCs, allocates all display
  channels, then tears down. Device Manager: Code 43, DxgkDdiStartDevice
  `STATUS_INSUFFICIENT_RESOURCES` (0xC000009A). Nothing rendered yet.
- **Three gates found and cleared, each bisected:**
  1. **VBIOS.** The PROM window must carry the card's flash chain including the second 0xE0
     FWSEC image with the real ucode bytes; headers or tables alone fail like the 127 KiB PCI ROM.
     Not required: the 0x70 image, the second flash copy, the tail. Cost: none, the window is read
     once at driver start. [VBIOS-BISECT.md](win11-2026-09-25/night-2026-09-25/VBIOS-BISECT.md),
     dump [prom-window-2026-09-25.md](../reference/rtx2070/prom-window-2026-09-25.md).
  2. **Registry.** `EnableGpuFirmware` and `RMEnableGpuFirmware` = DWORD 1 under
     `Services\nvlddmkm`, its `Parameters` and the class key `0007` switch 617.14 from the CPU-RM
     falcon chain (FWSEC on GSP, ACR on PMU, 60 s ENGCTL stall) to GSP-RM (Booter on SEC2, GSP
     queues, RPCs). [ANALYSIS-gsp-path.md](win11-2026-09-25/night-2026-09-25/ANALYSIS-gsp-path.md),
     [regkey-test.log](win11-2026-09-25/night-2026-09-25/regkey-test.log).
  3. **GR profile.** An empty KGR static profile (gpcMask 0) made `_kgrAlloc` fail with the same
     status. Fixed by answering the KMD's info controls with the card's real values
     ([kmd-controls-2026-09-26.md](../reference/rtx2070/kmd-controls-2026-09-26.md), 184 controls,
     replayed from `chips/tu106/recorded-controls.tsv` on branch `win-loop-2026-09-26`).
- **Current stop (Y0 to Y21, always the same):** after GSP_INIT the KMD allocates NVC570 core,
  8 window, 8 window-immediate and 4 cursor channels, clears 4 KiB through BAR1/BAR2, waits
  about 100 ms without a new RPC, then frees everything and sends GSP_SUSPEND (INIT to SUSPEND
  1.5 s). It never writes a display channel PUT. The guest log says only "insufficient system
  resources"; the DbgPrint trace (Y19) has no nvlddmkm text.
- **Ruled out, one run each:** extended config space, 0x110abc, PCIe root port, VGA role, T4
  identity, PMU model variants, the host RM answering every info control (Y13/Y14: the real card
  answered 84 controls, same stop), hotplug config (Y14), headless (Y15: another road, fails at
  NVDEC), 2 GiB FB (Y16), RUSD page (Y17), compbit store (Y20).
  [WINDOWS-LOOP.md](win11-2026-09-25/night-2026-09-25/WINDOWS-LOOP.md) has every iteration.
- **Open candidates, in order:**
  - The display controls the device still refuses: 0x730285 x9 (ACPI DOD port attachment),
    0x73013d (display ids with mux), 0x73014b (sideband I2C), 0x73117a. Y21 answers them (running).
  - Display channel state after the alloc: the KMD may poll a channel state or notifier the model
    never sets (guess; the 100 ms silence fits a timeout).
  - The private controls 0x2080a70a/a709/a801/a02f, 0x20803c01, 0x20808524.
  - Full host execution. Needs a device mode in which the guest speaks GPAs (Windows has no
    `caraxes_dma_range`); the capped binary `/mnt/vmstore/caraxes/win11/vfio-user-nvgpu-cap` and
    the identity DMA table are prepared.
- **Astra:** both reviews are in [astra-review-2026-09-26.md](../../docs/research/astra-review-2026-09-26.md);
  the registry finding came from the first, the control ids were checked against the headers.
- **Tooling that now works autonomously:** guest agent (PowerShell as SYSTEM, file transfer),
  QMP screendump and keys, ETW and DbgPrint capture, one-boot-per-configuration night runs with
  baseline diff ([README.md](win11-2026-09-25/README.md), `night-win*.sh`, `qga.py`, `qmp.py`).

## Linux (Cloud Hypervisor, vm4-615, 615 guest driver, `caraxes/runs/nvenc-2026-09-25/`)

- **Works:** desktop, Vulkan, CUDA, NVENC in Sunshine, Moonlight streams. Merged to main tonight:
  pool lock ([vm4-615-poollock](nvenc-2026-09-25/vm4-615-poollock/NOTES.md)), exclusion release,
  invalidate gate ([execution.md §8](../../docs/caraxes/execution.md)).
- **Fixed:** BAR1 pool lock hold (slow polls 0.04 to 0.19 %); exclusion release ordered after the
  host TSG free (VA-alloc bursts gone); new GPU work completes while streaming, 6 of 6
  ([vm4-615-invhold](nvenc-2026-09-25/vm4-615-invhold/NOTES.md)).
- **Not the cause:** the MMU-invalidate hold. The gate is in anyway (41491 busy reads, none past
  1 s, 0 Xid) and the streaming cap stayed.
- **Still open:**
  - **Streaming cap and cursor lag: cause found at 02:15, fix built, GPU test queued.** The
    per-frame timeline (kick, flip latch, vblank, next kick; `caraxes/tools/display-pace.py`)
    shows the display model on time: tick period 16.666 ms, 2212 of 2294 flips latch at the first
    tick after their kick, none late. The frame is lost between the latch and the guest's next
    kick: 20 to 22 ms without a client, 33 to 54 ms while streaming, where 60 Hz needs under 15.
    Right before each kick the compositor's commit does about 23 BAR2 flush reads (`R bar3
    0x00fea000`) and 2 MMU invalidates, and every trapped flush read ran a full BAR2 memfd sync
    (mean 174 us, 377327 syncs = 65.6 s per session, about 317/s), 7 to 13 ms per frame. Fix
    (branch `worktree-agent-af3f69b70fa0e2e7a`, 02c0a625, binary `-flippace-02c0a625`): a flush
    read only marks the sync as owed; the next hand-over (MMU invalidate, GSP or channel doorbell)
    or a 1 ms clock settles it; knob `CARAXES_BAR2_MEMFD_DEFER_FLUSH=0` restores the old path for
    the A/B. Expected: pre-kick run 1.5 to 3 ms, no-client cursor at 55+ kicks/s. While streaming
    the rest of the gap is Sunshine's serial per-frame chain (EGL import, CUDA, NVENC, map and
    unmap), so the cap may stay below 45 kicks/s until the scanout import cache from
    `sottr-stage.md` §11 lands. Docs: `docs/caraxes/display-pacing.md` in that worktree; the A/B
    lands in `vm4-615-flippace/NOTES.md`. Earlier attribution to Sunshine's capture pacing
    ([vm4-615-latency](nvenc-2026-09-25/vm4-615-latency/NOTES.md)) is superseded.
    **A/B verdict (03:14, [vm4-615-flippace](nvenc-2026-09-25/vm4-615-flippace/NOTES.md)):**
    the no-client display is fixed at 60 Hz (59.6 kicks/s in both deferred cells, 99 to 100 %
    one-tick frames, latch to kick p50 2.3 ms; old path 31 to 35/s). Streaming is about twice as
    fast (cursor 26 to 35 kicks/s against 11 to 13, Sunshine 41 to 49 ms against 62 to 81) but
    still below 45; the remaining time sits before the pre-kick run (18 to 29 ms against a run of
    1.4 to 2.0 ms), which is Sunshine's capture chain in the guest. Syncs fell from 411/s to 103
    to 116/s. Host NVRM/Xid silent, no TLB failures.
    **Regression, so not merged as default:** with the deferral, new GPU work while streaming
    fails 0 of 4 (vkcube aborts in device creation, glmark2 renders nothing); the same binary
    with `CARAXES_BAR2_MEMFD_DEFER_FLUSH=0` 1 of 1, the synchronous build 6 of 6. That abort is
    the cross-client stall from the CUDA x Vulkan item below, so the synchronous flush-read sync
    is what makes the second client's awaited memory visible; the pacing agent is listing the
    host-to-guest paths of that sync and building a variant that keeps the 60 Hz.
  - Guest CPU: the trap leaders are the usermode TIME reads 0xbb0080/84 (640 to 760/s), the BAR2
    flush read (310 to 710/s) and the MMU-invalidate triple. Zero-trap work for these is next.
    Interrupt page off soft-locks the 615 guest (bug, not a tuning knob).
  - **CUDA x Vulkan, the SotTR "signal 6": cause narrowed at 02:40.** The c5c0 status 0x57 is a
    symptom: an instrumented 615.71.09 guest module (built in the guest, then removed again)
    shows it is the resource server's parent lookup on a GR channel the Vulkan client had already
    freed itself. The real bug is a **stall: while one GR/compute client is active, a second
    client's initialisation makes no progress** (11 s without a doorbell on its channels, then the
    Vulkan driver tears down; the other way round the CUDA NVENC probe hangs 60 s beside vkcube).
    The device's GR answers are ruled out (promote, preemption mode, zcull bind echoed NV_OK; no
    per-client state in the static controls). Reproduced once in seven runs; the stock module
    showed the same stall as a hung vkcube. Next: find what the second client waits on
    (semaphore or notifier of another client, an undelivered event, or host-side serialisation of
    a second GR TSG; the stage's host watch also SIGTERMed the device twice because host
    `nvidia-smi` took over 3 s while CUDA and Vulkan ran together, which points at the host RM
    lock). Also found: the global context buffers' PA is stored under the first channel's key and
    dropped with it (`channel.rs`), so later mirror replays carry VA-only entries; a per-GPU store
    fixes that. [vm4-615-cuda-vulkan](nvenc-2026-09-25/vm4-615-cuda-vulkan/NOTES.md), merged.
    Narrowed further at 03:00 from the two ioctl logs: a clean device creation goes preemption
    mode, two `0xd01` root controls, ZBC table reads, c5c0; the failing one has a third `0xd01`
    (flags 0) and then unbinds the semaphore surface from its first GR channel and frees it before
    the ZBC reads, so the UMD is already on an error path there, and the c5c0 on the stale handle
    is just its continuation. The 11 s sit between the preemption-mode control and that unbind,
    without any RPC or doorbell: a kernel-side wait inside one of those ioctls or a user-mode poll
    on memory the device backs. The agent identifies `0xd01`, times the ioctls and names the poll.
  - The concurrency matrix (CUDA-only ladder, headless, with head, Sunshine without client,
    streaming; per-cell rmioctl logs and device trace around failures) is prepared and runs after
    the pacing A/B; it is also the data set for the stall question above.
