## Windows (QEMU 11.1 `vfio-user-pci`, driver 617.14, `caraxes/runs/win11-2026-09-25/`)

- **State:** the driver boots the GSP-RM path, exchanges ~500 RPCs, allocates all display
  channels, then tears down. Device Manager: Code 43, DxgkDdiStartDevice
  `STATUS_INSUFFICIENT_RESOURCES` (0xC000009A). Nothing rendered yet.
- **Three gates found and cleared, each bisected:**
  1. **VBIOS.** The PROM window must carry the card's flash chain including the second 0xE0
     FWSEC image with the real ucode bytes; headers or tables alone fail like the 127 KiB PCI ROM.
     Not required: the 0x70 image, the second flash copy, the tail. Cost: none, the window is read
     once at driver start. [VBIOS-BISECT.md](win11-2026-09-25/night-2026-09-25/VBIOS-BISECT.md),
     dump [prom-window-2026-09-25.md](../reference/rtx2070/prom-window-2026-09-25.md).
  2. **Registry.** `EnableGpuFirmware` and `RMEnableGpuFirmware` = DWORD 1 under
     `Services\nvlddmkm`, its `Parameters` and the class key `0007` switch 617.14 from the CPU-RM
     falcon chain (FWSEC on GSP, ACR on PMU, 60 s ENGCTL stall) to GSP-RM (Booter on SEC2, GSP
     queues, RPCs). [ANALYSIS-gsp-path.md](win11-2026-09-25/night-2026-09-25/ANALYSIS-gsp-path.md),
     [regkey-test.log](win11-2026-09-25/night-2026-09-25/regkey-test.log).
  3. **GR profile.** An empty KGR static profile (gpcMask 0) made `_kgrAlloc` fail with the same
     status. Fixed by answering the KMD's info controls with the card's real values
     ([kmd-controls-2026-09-26.md](../reference/rtx2070/kmd-controls-2026-09-26.md), 184 controls,
     replayed from `chips/tu106/recorded-controls.tsv` on branch `win-loop-2026-09-26`).
- **Current stop (Y0 to Y21, always the same):** after GSP_INIT the KMD allocates NVC570 core,
  8 window, 8 window-immediate and 4 cursor channels, clears 4 KiB through BAR1/BAR2, waits
  about 100 ms without a new RPC, then frees everything and sends GSP_SUSPEND (INIT to SUSPEND
  1.5 s). It never writes a display channel PUT. The guest log says only "insufficient system
  resources"; the DbgPrint trace (Y19) has no nvlddmkm text.
- **Ruled out, one run each:** extended config space, 0x110abc, PCIe root port, VGA role, T4
  identity, PMU model variants, the host RM answering every info control (Y13/Y14: the real card
  answered 84 controls, same stop), hotplug config (Y14), headless (Y15: another road, fails at
  NVDEC), 2 GiB FB (Y16), RUSD page (Y17), compbit store (Y20).
  [WINDOWS-LOOP.md](win11-2026-09-25/night-2026-09-25/WINDOWS-LOOP.md) has every iteration.
- **Open candidates, in order:**
  - The display controls the device still refuses: 0x730285 x9 (ACPI DOD port attachment),
    0x73013d (display ids with mux), 0x73014b (sideband I2C), 0x73117a. Y21 answers them (running).
  - Display channel state after the alloc: the KMD may poll a channel state or notifier the model
    never sets (guess; the 100 ms silence fits a timeout).
  - The private controls 0x2080a70a/a709/a801/a02f, 0x20803c01, 0x20808524.
  - Full host execution. Needs a device mode in which the guest speaks GPAs (Windows has no
    `caraxes_dma_range`); the capped binary `/mnt/vmstore/caraxes/win11/vfio-user-nvgpu-cap` and
    the identity DMA table are prepared.
- **Astra:** both reviews are in [astra-review-2026-09-26.md](../../docs/research/astra-review-2026-09-26.md);
  the registry finding came from the first, the control ids were checked against the headers.
- **Tooling that now works autonomously:** guest agent (PowerShell as SYSTEM, file transfer),
  QMP screendump and keys, ETW and DbgPrint capture, one-boot-per-configuration night runs with
  baseline diff ([README.md](win11-2026-09-25/README.md), `night-win*.sh`, `qga.py`, `qmp.py`).

## Linux (Cloud Hypervisor, vm4-615, 615 guest driver, `caraxes/runs/nvenc-2026-09-25/`)

- **Works:** desktop, Vulkan, CUDA, NVENC in Sunshine, Moonlight streams. Merged to main tonight:
  pool lock ([vm4-615-poollock](nvenc-2026-09-25/vm4-615-poollock/NOTES.md)), exclusion release,
  invalidate gate ([execution.md §8](../../docs/caraxes/execution.md)).
- **Fixed:** BAR1 pool lock hold (slow polls 0.04 to 0.19 %); exclusion release ordered after the
  host TSG free (VA-alloc bursts gone); new GPU work completes while streaming, 6 of 6
  ([vm4-615-invhold](nvenc-2026-09-25/vm4-615-invhold/NOTES.md)).
- **Not the cause:** the MMU-invalidate hold. The gate is in anyway (41491 busy reads, none past
  1 s, 0 Xid) and the streaming cap stayed.
- **Still open:**
  - Streaming cap: compositor at 10 to 20 kicks/s while streaming, Sunshine 53 to 77 ms, cursor
    lag. The kick rate appears to follow Sunshine's KMS capture pacing
    ([vm4-615-latency](nvenc-2026-09-25/vm4-615-latency/NOTES.md)); the pacing agent is measuring
    kick, flip latch, vblank and next kick.
  - Guest CPU: the trap leaders are the usermode TIME reads 0xbb0080/84 (640 to 760/s), the BAR2
    flush read (310 to 710/s) and the MMU-invalidate triple. Zero-trap work for these is next.
    Interrupt page off soft-locks the 615 guest (bug, not a tuning knob).
  - CUDA x Vulkan: a live CUDA context makes device creation fail (class c5c0, status 0x57 from
    the guest kernel, no RPC reaches the device); this is the SotTR "signal 6" under Sunshine
    ([vm4-615-vulkan](nvenc-2026-09-25/vm4-615-vulkan/NOTES.md)). The DKMS package ships the RM
    core prebuilt, so the instrumented module needs the full 615.71.09 source (agent running).
  - The concurrency matrix (several CUDA contexts, headless, with head, streaming) is queued
    behind it.
