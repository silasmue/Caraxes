# GSP boot path by architecture family (GA10x / AD10x / GH100 / GB10x-GB20x)

All paths relative to `vendor/open-gpu-kernel-modules/`. Turing (TU102/TU106) internals are covered by [gsp-boot-turing.md](gsp-boot-turing.md) and not repeated here except as a baseline. Every claim below is a literal grep/read from the tree, not inference from vendor docs.

## 0. Chip grouping used by the HAL tables

The generated NVOC/rmconfig tables group chips almost identically everywhere: **{TU102/104/106/116/117, GA100}** vs **{GA102/103/104/106/107, AD102/103/104/106/107}** vs **{GH100}** vs **{GB100/102/10B/110/112, GB202/203/205/206/207/20B/20C, GR100/102}**. The Turing/Ampere-GA100 line and the GA102+/AD10x line share almost all Turing boot logic; the real break is at Hopper.

## 1. HAL implementations that differ from Turing

`src/nvidia/src/kernel/gpu/gsp/arch/*/` files: `ampere/kernel_gsp_ga100.c`, `ampere/kernel_gsp_ga102.c`, `ampere/kernel_gsp_falcon_ga102.c`, `ada/kernel_gsp_ad102.c`, `hopper/kernel_gsp_gh100.c`, `blackwell/kernel_gsp_gb100.c`, `blackwell/kernel_gsp_gb10b.c`, `blackwell/kernel_gsp_gb202.c`, `blackwell/kernel_gsp_ecc_gb100.c`, `rubin/kernel_gsp_ecc_gr100.c` (Rubin/GR10x has no separate boot-path file; it reuses GH100/GB100 boot HALs, only ECC differs).

**Assessment for §1:** FWSEC/FRTS parsing from the VBIOS ROM and the SEC2-hosted Booter Load/Unload flow are **unchanged all the way through Ampere and Ada**; only the low-level "execute an HS falcon binary" primitive changes (Turing: loader/DIRECT bootType via legacy SEC2 signature check; GA102+: BOOT_FROM_HS via hardware BROM/PKC3K, same SEC2 target). GH100 replaces the whole thing with GSP-FMC: no FWSEC/FRTS, no Booter, WPR is set up by ACR/FSP from a `GSP_FMC_BOOT_PARAMS` struct stuffed into GSP mailbox regs, and the CPU only points the RISCV BootROM (BCR) at the FMC image (`kernel_gsp_gh100.c:718-777`). Blackwell/Rubin reuse the Hopper flow with only WPR2-readout and reset-PLM differences.

## 3. Message queue / RPC differences

- **Vocabulary is architecture-independent.** `src/nvidia/inc/kernel/vgpu/rpc_global_enums.h` (X-macro of `NV_VGPU_MSG_FUNCTION_*`) and `src/nvidia/generated/g_rpc-structures.h` (versioned structs like `rpc_set_guest_system_info_v03_00`, `rpc_get_gsp_static_info_v14_00`, `rpc_init_done_v17_00`) contain **zero** chip conditionals (`grep -c '^#if' rpc_global_enums.h` = 5, all include guards; none mention TU10X/GA10X/etc.). `SET_GUEST_SYSTEM_INFO`/`GET_GSP_STATIC_INFO`/`GSP_INIT_DONE` are the same RPCs and struct layouts on every family; `kgspBootstrap_GH100` even sends them *before* boot completes (`kgspSendInitRpcs`, `kernel_gsp_gh100.c:956-964`) instead of after, unlike Turing/Ampere's post-boot ordering.
- **LIBOS version boundary**: LIBOS2 for TU102-GA100, LIBOS3 for everything GA102 and later (table in §1); this changes the GSP-side task layout but the CPU-side `message_queue_cpu.c` queue/header code itself has no libos-version branch (`grep KGSP_LIBOS_VERSION message_queue_cpu.c` finds nothing); the difference is confined to which firmware image and init-args struct version is used.
- **"CPU sequencer" RPCs (reverse direction, GSP to CPU) differ**: `NV_VGPU_MSG_EVENT_GSP_LOAD_EXEC_GENERIC_BOOTLOADER` maps to `kgspLoadAndExecuteGenericBootloader_HAL`, implemented only for TU102-GA100 (`g_kernel_gsp_nvoc.c:2060`, stub elsewhere at `:2065`); `NV_VGPU_MSG_EVENT_GSP_LOAD_EXEC_HS_BINARY` maps to `kgspLoadAndExecuteHsBinary_HAL`, implemented only for GA102+/AD10x (`kernel_gsp_falcon_ga102.c:311`, HAL selector `g_kernel_gsp_nvoc.c:2083`, stub for Turing at `:2079` and for GH100+). So Turing's GSP can ask the CPU to run a generic bootloader; GA10x/AD10x's GSP can ask the CPU to run an HS binary; GH100+ never sends either (ACR/FSP does it all on-die). The `GspLoadExecHsBinaryParams`/`GspLoadExecGenericBootloaderParams` structs live in `src/nvidia/arch/nvalloc/common/inc/rmgspseq.h`, only included by the turing/ampere falcon files.
- The actual register write that signals a new command (`kgspSetCmdQueueHead_HAL`, called after every send, `kernel_gsp.c:424`) is chip-HAL'd but only by register offset, not by protocol; not separately audited here (medium-thoroughness scope).

## 4. vGPU-VF paravirtual front end

- `PDB_PROP_GPU_VGPU_OFFLOAD_CAPABLE` is set to `NV_TRUE` **only** for `AD102-AD107, GH100, and all Blackwell/Rubin (GB100/102/10B/110/112, GB202-207/20B/20C, GR100/102)`, explicitly **excluding Turing and Ampere (GA100/GA102-107)** (`src/nvidia/generated/g_gpu_nvoc.c:415-424`, read at `src/nvidia/src/kernel/gpu/gpu_registry.c:141`). This flag is a **PF-side** "can this chip offload vGPU-plugin work to GSP-RM" capability, not the guest-VF driver's own code path; it is never set anywhere else in this open-source tree, i.e. the actual host-side vGPU manager that would flip it on lives outside this repo.
- The **guest VF driver identity** is a separate axis, `RmVariantHal: VF`, which stubs out essentially the entire `KernelGsp` HAL surface (`kgspBootstrap_5baef9`, `kgspExecuteBooterLoad_5baef9`, `kgspAllocBootArgs_5baef9`, `kgspTeardown_5baef9`, etc.; every table in §1 has a `RmVariantHal: VF` branch first). A VF build never touches falcon/RISCV boot registers at all.
- Instead, `src/nvidia/src/kernel/vgpu/rpc.c` drives a paravirtual RPC transport: `initRpcInfrastructure_VGPU` (`rpc.c:1663`) sets up shared memory, and requests are signalled with `rpcVgpuGspRingDoorbell_HAL`/`rpcVgpuGspWriteScratchRegister_HAL`, which write `NV_VIRTUAL_FUNCTION_PRIV_DOORBELL` and `NV_VIRTUAL_FUNCTION_PRIV_MAILBOX_SCRATCH(NV_VF_SCRATCH_REGISTER_GUEST_RPC_HI/LO)` (`src/nvidia/src/kernel/vgpu/arch/ampere/rpcga102.c:35-50`, regs from `published/ampere/ga102/dev_vm.h`). This HAL is selected by ChipHal at GA102 (`g_rpc_private.h:4313-4314`), stubbed for TU10X/GA100 (`:271,292`); so the VF doorbell mechanism exists from Ampere onward, one architecture generation *before* `VGPU_OFFLOAD_CAPABLE` turns on for the PF side; the two properties are not the same gate.
- **Would a synthetic AD10x/GB10x device skip firmware boot via VF?** No. Going the VF route does not avoid emulating firmware, it trades it for a much bigger problem: a VF only works because a **real PF is already running full GSP-RM** and exposing an SR-IOV VF BAR with the doorbell/scratch registers above; the VF guest never boots anything, it just RPCs into an already-booted GSP-RM instance on the other side of that doorbell. An emulator standing in for "the device" would have to *be* that already-booted GSP-RM (implement the entire RM control/object/alloc RPC surface as a server), not merely fake a few boot registers. That is strictly more work than emulating the Turing/Ampere/Ada firmware boot sequence, so the VF path is a dead end for this project's goal.

## 5. Firmware binaries required per family

- **Small, chip-specific bootstrap ucodes** are compiled directly into the driver as NVOC bindata (`src/nvidia/generated/g_bindata_kgspGetBinArchive*.c`), one set per HAL bucket: `BooterLoadUcode`/`BooterUnloadUcode` exist for `TU102, TU116, GA100, GA102, AD102` only (no GH100+ entries; confirms §1); `GspRmBoot` (the tiny stub that starts GSP-RM) exists per family `TU102, GA100, GA102, AD102, GH100, GB100, GB10B, GB202, GB20B, GR100`; Hopper+ additionally ship `ConcatenatedFMC[Desc]`, `GspRmFmcGfwProdSigned/DebugSigned`, and `GspRmCcFmcGfwProdSigned` (the actual GSP-FMC/ACR image that the RISCV BootROM DMAs in) for `GH100, GB100, GB10B, GB202, GB20B, GR100`.
- **The large GSP-RM firmware ELF** is *not* embedded; it is fetched from disk at runtime via `nv_get_firmware()` (`osinit.c:1899`, called from `RmFetchGspRmImages`, `osinit.c:1880-1958`), named by chip family via `nv_firmware_for_chip_family()` (`src/nvidia/arch/nvalloc/common/inc/nv-firmware.h:85-119`): `{TU10X,TU11X,GA100}` use `gsp_tu10x.bin` / `ucodes_tu10x.bin`; `{GA10X, AD10X, GH100, GB10X, GB20X, GR10X, GB10Y, GB20Y}` use `gsp_ga10x.bin` / `ucodes_ga10x.bin`. **One firmware package is shared from Ampere-GA10x through Hopper and all announced Blackwell/Rubin variants.** The chip-to-family mapping is `src/nvidia/arch/nvalloc/common/inc/nv-firmware-chip-family-select.h:33-75`.

## Assessment: which non-Turing identity is least work

**Ampere GA10x (e.g. GA102) is the smallest next step**, not Ada or Hopper: `kgspBootstrap`, `kgspPrepareForFwsecFrts`, `kgspExtractVbiosFromRom`, `kgspIsWpr2Up`, `kgspWaitForGfwBootOk`/`gpuWaitForGfwBootComplete`, and the Booter Load/Unload flow are all byte-for-byte the *same* HAL implementations as Turing (`_TU102`), so the FWSEC/FRTS/Booter-over-SEC2/GFW_BOOT-scratch-register choreography an emulator already models for TU106 carries over unchanged. The only new things to fake are: (a) the BROM/PKC3K registers (`NV_PFALCON2_FALCON_BROM_*`) used by the changed `kgspExecuteHsFalcon_GA102`/`kgspLoadAndExecuteHsBinary_GA102` primitive, (b) `kgspConfigureFalcon_GA102`'s different `bBootFromHs=TRUE`/register-base scheme, and (c) switching the served firmware file from `gsp_tu10x.bin`/LIBOS2 to `gsp_ga10x.bin`/LIBOS3 plus new per-chip `GspRmBoot`/`BooterLoadUcode`/`BooterUnloadUcode` bindata. **Ada (AD10x)** adds only one more real difference on top of that (the AD102-only scrubber-via-SEC2 step, `kgspExecuteScrubberIfNeeded_AD102`, conditionally invoked). **Hopper and Blackwell/Rubin are a much bigger jump**: FWSEC/FRTS/Booter disappear entirely, replaced by GSP-FMC + BootROM BCR registers + FSP/SEC2 "boot command" indirection + lockdown-release polling + optional SPDM session establishment; effectively a new boot model, not a HAL variant of the existing one.

## 6. GSP RPC API stability across architectures and driver versions

**(a) Vocabulary/struct sharing.** `src/nvidia/inc/kernel/vgpu/rpc_global_enums.h` (the `NV_VGPU_MSG_FUNCTION_*` X-macro list) and `src/nvidia/generated/g_rpc-structures.h` (all `rpc_*_v##_##` payload structs, generated from `inc/kernel/vgpu/rpc-structures.def` per its header comment, `g_rpc-structures.h:26-28`) contain no chip conditionals at all; `grep -n "TU10X\|GA10X\|AD10X\|GH100\|GB10"` over both files returns nothing. `g_rpc-message-header.h` defines exactly one wire header, `rpc_message_header_v03_00` (fields: `header_version, signature, length, function, rpc_result, rpc_result_private, sequence, u, rpc_message_data[]`), used unconditionally as `rpc_message_header_v` everywhere (`g_rpc-message-header.h:39-51`). This is a single, driver-release-wide ABI, not a per-architecture capability description.

**(b) Per-architecture RPC files.** Only `src/nvidia/src/kernel/vgpu/arch/ampere/rpcga102.c` and `.../maxwell/rpcgm204.c` exist under `vgpu/arch/`. `rpcga102.c` implements exactly two functions, `rpcVgpuGspRingDoorbell_GA102`/`rpcVgpuGspWriteScratchRegister_GA102` (`rpcga102.c:35-50`), selected by ChipHal at GA102 in the legacy rmconfig table `g_rpc_private.h` (`rpcHalIfacesSetup_GA102`, `:4310-4314`; STUB for TU10X/GA100 per the comment at `:270-271,291-292`). `rpcgm204.c` implements one legacy wrapper (`rpcGetEngineUtilizationWrapper_GM204`, unrelated to boot). **No other RPC entry point in `g_rpc_private.h` is chip-conditioned**: the file's ~150 other `RpcCtrlXxx_v##_##` / `_STUB` pairs (e.g. `rpcCtrlGrmgrGetGrFsInfo`, `rpcAllocMemory`, `rpcSetPageDirectory`) all resolve to `_STUB` for *every* chip in this build profile (`Profile: shipping-gpus-openrm`, `g_rpc_private.h:5`; e.g. `rpcHalIfacesInitStruct_GA100`, `:4296-4301`). These per-message-version symbols exist for a different consumer (a host-side vGPU-plugin compatibility profile that is not built in this tree); in the GSP-client profile actually used here, generic RM control calls go through one non-versioned passthrough RPC, not these per-command wrappers.

**(c) Message versioning.** Struct names carry a schema version (`rpc_set_guest_system_info_v03_00` `g_rpc-structures.h:36`, `rpc_get_gsp_static_info_v14_00` `:377`, `rpc_init_done_v17_00` `:1589`) that is bumped when a message's *payload* changes across driver releases, not per architecture; confirmed by (a). The CPU driver does **not** runtime-check `rpc_message_header_v.signature` or `.header_version` anywhere (`grep -n "header_version\|->signature" message_queue_cpu.c kernel_gsp.c rpc.c` finds nothing); it checks the MCTP header version and the NVDM vendor id on every received element (`message_queue_cpu.c:737-759`; corrected on 2026-09-23 by [gsp-abi-610.md](gsp-abi-610.md), which had this as a CrashCat-only check). `GspFwWprMeta` similarly has one fixed revision/magic pair, `GSP_FW_WPR_META_REVISION 1` / `GSP_FW_WPR_META_MAGIC 0xdc3aae21371a60b3` (`src/nvidia/arch/nvalloc/common/inc/gsp/gsp_fw_wpr_meta.h:211-212`), asserted to be exactly 256 bytes on every architecture (`ct_assert(sizeof(*pWprMeta) == 256)`, `kernel_gsp_gh100.c:314`); no per-arch struct variant.

**(d) Firmware/driver version lock.** `_kgspFwContainerVerifyVersion` (`kernel_gsp.c:5719-5774`) reads the `.fwversion` ELF section out of the fetched `gsp_*.bin` and requires it to **exact-string-match** the driver's own `NV_VERSION_STRING` (`:5753-5771`); any mismatch is a hard `NV_ERR_INVALID_DATA` before boot proceeds. This check is architecture-independent; it is the sole mechanism keeping GSP firmware and CPU-side RPC structs in lockstep, and it pins to a whole driver package release, not a negotiated ABI version. Binary sharing (§5): `gsp_tu10x.bin` serves `TU10X, TU11X, GA100`; `gsp_ga10x.bin` serves `GA10X, AD10X, GH100, GB10X, GB20X, GR10X, GB10Y, GB20Y` (`nv-firmware.h:88-119`, `nv-firmware-chip-family-select.h:33-75`), i.e. one firmware/RPC-ABI generation spans five hardware generations.

**Conclusion.** The GSP RPC layer is **one driver-version-wide ABI with architecture-conditional transport, not a per-architecture capability description**: the message vocabulary, struct layouts, and version numbers are fixed by driver release and shared unconditionally across chips; only the physical means of poking the queue doorbell (`kgspSetCmdQueueHead_HAL`) and the VF paravirtual doorbell/scratch registers (§4b) are chip-HAL'd. For an emulator building a GSP-RM server the way `crates/nvrm-sys` generates the ioctl ABI per driver version: the **RPC vocabulary/struct set (`rpc_global_enums.h`, `g_rpc-structures.h`, `g_rpc-message-header.h`) should be generated once per vendored driver version**, exactly like the ioctl headers; it does not need per-architecture variants. What *does* need per-architecture branches is strictly the boot-time register sequence (§1–§2) and, if ever pursued, the VF doorbell transport (§4); everything past `GSP_INIT_DONE` can be treated as architecture-agnostic for a given driver version.
