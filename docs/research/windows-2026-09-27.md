## Current status and the earlier headless result

KD3 isolated a fixed-address allocation failure inside the Windows guest RM:
908.5 MiB at FB offset 0 returned `NV_ERR_NO_MEMORY`. Caraxes advertises usable
FB at `[0x1a9800000, 0x1e9600000)` for this reservation. Changing only that one
request's offset to `0x1a9800000` in KD made the allocation succeed. Continuing
that diagnostic run still returned `0xC000009A` later in startup. KD3 has been
stopped; subsequent stock-driver runs used no request edit. This establishes an address
mismatch for one allocation, not a working stock Windows desktop. It provides
no evidence of a device whitelist. See the
[KD checkpoint](../../caraxes/runs/windows-kd-2026-09-27/README.md#fixed-address-allocation-controlled-diagnostic)
for the call chain, parameters and limits of the experiment.

KD4 and KD5 also returned `0xC000009A` without guest parameter edits. A write
watch confirmed that Windows copies its zero cached base into the allocation
segment despite knowing the high usable FB bounds. KD5 reports
`consoleMemSize=0`, so a leading owned console carveout alone cannot activate
the public RM heap-start calculation. KD6 traced the cached base to a successful
legacy `FB_GET_INFO` query, index `0x1e` (HEAP_START), and again returned
`0xC000009A`. The result is zero before segment construction.

KD7 tests the [experimental zero-based FB mode](../vfio/zero-based-fb.md):
guest addresses map to offsets within the same owned host reservation, with
shadow-only execution. The first boot still returned `0xC000009A` without hitting
the previously observed `+0x185baa4` allocation-failure branch. A PnP restart reached the
`+0x186628b` failure branch after `+0x185a0a0` returned false. A second restart
reached `+0x185bd42` with `SIL=1`: the previously failing heap/allocation function
now succeeds without guest-memory edits. Missing the old breakpoint therefore
meant avoiding its failure branch, not skipping the function. A later startup
failure is now traced to a zero-sized tone-mapping resource: all emulated window
capabilities clear `TMO_PRESENT`, so the Windows initializer accumulates no
storage and rejects the resource. The TMO diagnostic variant makes that allocation succeed (36 KiB), but then
reveals an inconsistent ILUT descriptor caused by missing CAPB geometry. These
are diagnostic capability changes; LUT color processing is not implemented.
There is still no hardware rendering result. No new host Xid was observed.

Later host-backed trials through B11 still report NVIDIA Code 43; see
[stability-results-2026-09-27.md](stability-results-2026-09-27.md). The pause after
B3 described below belongs to that earlier experiment, not the current test state.

B4 reached NVIDIA PnP code 0 and appeared in DXGI, but did not render:

- `WIN_HOST_MODE=emu`, `WIN_GPU_DISPLAY=0`; no host GPU execution.
- PCI class remained `0300` (VGA). Disabling the display model did not change it
  to `0302` (3D controller).
- NVIDIA D3D11 device creation returned `0x887a0004`. Microsoft software adapters
  succeeded; they do not count as a NVIDIA rendering result.
- B6 used the same VGA identity with display disabled and host execution enabled.
  It returned NVIDIA Code 43 and exposed only Microsoft software adapters in DXGI.
- The separate historical class-0302 experiment F did not establish a successful

The acceptance gate is a host-backed NVIDIA WDDM adapter, successful hardware
D3D/Vulkan rendering and a usable Windows desktop. PnP code 0 alone is insufficient.

## Corrections and limits

- Display DMA channels honor the allocation's initial PUT/GET offset. PIO bytes
  at that offset belong to a pointer, not a DMA offset.
- IHUB resource geometry comes from the [read-only capture](../../caraxes/reference/rtx2070/display-caps-2026-09-27.txt):
  5120 entries of 128 bytes, 128-byte line requests. Unimplemented physical feature
  bits are not copied. This is a consistency correction, not a demonstrated Code 43 fix.
- VFIO IRQ disable drops both owned eventfd copies; a later arm still works.
- Adaptive BAR1 access splitting uses the mapping's actual size after allocation
  fallback; release builds check raw window bounds before pointer access.
- `SET_DEFAULT_VASPACE` records and validates the device's live VAS association.
  An empty server-owned interval at PA 0 preserves the last usable root.
- QEMU GPA mode registers exact 4 KiB-aligned RAM fragments immediately, without
  waiting for all installed RAM or inserting hole fillers. The Linux module's
  table constructor and 2 MiB contract remain separate.
- GPA mapping changes are supported before descriptor use. After a host object
  or cached descriptor snapshot can depend on them, changes are refused for the
  remainder of that device process. Dynamic remapping/hotplug needs a later
  quiesce-and-cache-invalidation protocol; this change does not claim that support.
- Failed registration/publication rolls back; failed frees retain ownership and
  CPU mappings. Empty GPA tables deny DMA instead of falling back to identity.
- The D3D probe now passes an actual IDXGIAdapter interface pointer. Historical
`DXGI_ERROR_UNSUPPORTED` results need rechecking with this corrected probe.

After B3, read-only `nvidia-smi` reported 6693 MiB free VRAM and 232 MiB free BAR1,
with the host driver still bound. Further host-execution trials are paused pending
the first-channel fault diagnosis; subsequent checks use pure emulation. Xid 31/32
are evidence against claiming isolation/fault-containment acceptance for these runs.

`0x2080b202` identifies a VOLT legacy-nonprivileged interface, but its operation is
not named by public headers. Do not forward it opaquely to the host. Diagnostic
ACK traces now include the first 48 request bytes. Driver boot with broad ACKs is
not evidence of semantic compatibility or successful rendering.

B4's observed `0x2080b202` request prefixes are zero; that alone does not identify
GET versus SET or prove it causes the D3D failure. `0x2080a618` still fails the
615/610 pure-emulation layout check (20512 versus 20000 bytes).

## First host-channel fault: next diagnostic gate

The B3 kernel log records `intr1 00000004 HCE_DBG0 00000300 HCE_DBG1 0400258e`.
The public `clc5b5.h` identifies method `0x300` as `LAUNCH_DMA`; bit 13 in the
captured argument requests a physical destination. The mirror allocates an
ordinary user channel. NVIDIA's [TU104 PBDMA reference](https://github.com/NVIDIA/open-gpu-doc/blob/master/manuals/turing/tu104/dev_pbdma.ref.txt)
defines interrupt bit 2 as `HCE_PRIV`: a physical CE operation without channel
privilege. This identifies the reported fault as a channel-privilege mismatch
in Windows' CE-utils startup, rather than a failure to fetch this method.
It does not establish that all address mappings or later commands are correct.

Guest channel privilege must not directly grant host channel privilege. NVIDIA's
`kernel_channel.c` explicitly relies on VMMU/IOMMU isolation for privileged VF
channels. Before another host-execution trial, determine how to emulate these
physical operations or translate them into bounded operations on host-owned
allocations. Simply switching mirror allocation to admin would bypass the
address-space boundary on which shadow virtual mappings depend.

Disabling global CE-utils can isolate the next startup gate in a diagnostic run;
it is not a production compatibility fix. After resolving this path, require
D3D device creation and a verified hardware-rendered frame before desktop or
3DMark performance measurements. PnP code 0 and a QEMU fallback desktop do not
satisfy those gates.
