# The device lock's long holders, and the SotTR walk crawl (2026-09-29)

Scope: taking long holders off the device lock D (docs/caraxes/execution.md §9), what the new
attribution showed on Windows, a SotTR loading crawl on the lockfree line, and the levers that
followed. Branches: `lockfree-2026-09-29` (Windows line), `lockfree-pool-2026-09-29` (with the
BAR1 pool's P1-P4, Linux line). Evidence: `/mnt/vmstore/caraxes/alpha-2026-09-27/windows-plain/`
(`W/`), `/mnt/vmstore/caraxes/runs-2026-09-29/` (`R/`).

## Steps

- 0, 1 (8f691492): per-holder hold histogram (`dlock.rs`); a doorbell no longer waits for the
  shadow worker under D, it holds its ring and the completer thread forwards it (§9.1).
- 2 (a883c6f2): a channel's mirror build (TSG, channel, engine objects, GFXP, preemption) runs on
  the shadow worker; D only for the snapshot and the commit (schedule, token, ring; §9.2).
- Attribution in the same commit: every GSP RPC timed by function and command or class, doorbells
  by software or host, build phases (`dlock::work`); a long hold keeps tags of its work.
- 5a (dc30d2c5): the software executor translates a range per 2 MiB unit (`translate_pages`), and
  a software doorbell's time is split into translations and CPU copies (§9.6).

## Windows: what held D

- C63 (step 1): "doorbell/re-arm/rpc eventfds" 553 holds, 45.1 s, p50 32-64 ms, max 747 ms.
  Neither the RPC nor the re-arm eventfd was on, so these were channel doorbells; the 3227 GSP
  RPCs came as trapped BAR0 writes (1.76 s in total) [W/C63-lf/gpu.log, env.json].
- C65 (step 2): "doorbell software 357 x 21792 ms (max 537742 us)", "doorbell host 51 x 371 ms",
  "mirror build snapshot 5 x 370 ms (max 347 ms)", RPCs small. Longest holds: software doorbells
  of chid 15 (the KMD's paging channel) and chid 4, 277-537 ms [W/C65-lf3/gpu.log].
- The CE bytes behind them were small (57 memsets, 77 MiB), and the device CE's large transfers
  never wait under D. `GpuMem::pieces` walked 4-5 uncached table words per 4 KiB page through the
  BAR1 windows: the likely cost, which 5a removes and its split confirms or refutes.
- The 347 ms snapshot was `CARAXES_SHADOW_CHANNEL_DIAG=1`: its coverage query waits under D for
  the worker's whole set-A apply. Dropped from the Windows runs.

## SotTR: the walk crawl (0667070d, step 1 + pool)

- Loading screen for 20+ minutes. The game root 0xfc625000: 3328 full walks in 14558 syncs,
  6.5 M table reads, 1181 s of sync time; "vram store reads by caller: page tables 26.9 M reads,
  25.6 GB" [R/sottr-ab/C-poollf-0667070d/gpu-exit-early.log]. drsv3-on-2: 1 full walk.
- Cause: a page table in guest sysmem cannot be watched, and the walk cache made every update of
  such a root a full walk that also dropped its VRAM table copies. No change of the victim cache,
  the lockfree steps or the pool touches that trigger; the guest put tables in sysmem this time,
  most likely under VRAM pressure (3885/4096 MiB while loading). Inferred from the code; the next
  run counts it.
- Fix (60446c59 / 156bc567): the cache keeps the nodes whose table is in sysmem and re-reads only
  those at every update; the VRAM copies stay. Counted in each VAS teardown line.
- With it, `observable()` answers for such a root too (68d7f54c / 519eda49): its doorbells sync
  their channel's pages, not every live page.

## Lever 1: the invalidate syncs tables only (c475477a / fb6c134c)

- drsv3-on-2: 195193 invalidates with a flush owed ran full syncs, 93 s (477 us each), on the
  guest's invalidate path; a table-only sync cost 164 us. In the benchmark window: 624
  invalidates/s at 889 us of device time each.
- An engine consumes data only after an MMIO start write (doorbell, GSP command, BAR2 bind), each
  a sync point; the invalidate starts none. The owed flush now waits for the next start point or
  the 1 ms flush clock (bar2-memfd.md §3 rules 2 and 3).

- Run E (886a6041, with 5a and the breakdown): loading 2 min (game window to benchmark start;
  D had not finished loading after 10), but the benchmark 12.1 FPS (on-2 15.4). Each invalidate's
  table sync also ran the BAR1 pool's full replica merge (675 us, 144 s over the run; the table
  sync itself 446 us, 95 s), and the owed data flush moved to the flush clock (168k clock syncs,
  the clock held D 136 s): more lock time, not less [R/sottr-ab/E-lfpool-886a6041/gpu-exit.log].
- Fix (5e19f345): at an invalidate only the replicas whose home is a followed page table are
  merged; data replicas wait for the next engine start (bar2-memfd.md §3 rule 3).
- E's benchmark window, per second: trapped usermode doorbells 98 x 2.8 ms, invalidate writes
  197 x 1.4 ms, BAR2 syncs 436 x 361 us, TRIGGER reads 507 x 152 us (access times include the
  wait for D).

## The invalidate page (9b52ab1c)

- `CARAXES_INVALIDATE_PAGE=1`: the guest's PDB, UPPER and TRIGGER stores and its TRIGGER polls
  are memory; a held invalidate now completes on the `inv-complete` thread without D (§9.8).
- Not run yet; to be tried after the per-invalidate work under D is down.

## The posted doorbell

- SotTR run E: 98 trapped doorbells per second in the benchmark at 2.8 ms each (D wait
  included), 94k in the run (171 s); the token pool missed the game's channels (c8d47551 fixes
  the notifier index).
- The trapped doorbell now costs one BAR0 exit whatever the client does: the write is queued
  without D and rung by the completer; every later guest access rings the queue first (§9.9).
