# Display reserve through the dmem cgroup controller (2026-09-29)

Scope: the application cap of [display-balloon-2026-09-29.md](display-balloon-2026-09-29.md) built on the upstream dmem cgroup controller (the user's choice, 2026-09-29, over an NVIDIA balloon patch): the verified facts, the guest units, Linux B's kernel variant, the test plan, a host-side design note.

Abbreviations:
- `K` = Linux 7.2.7 (`/mnt/vmstore/caraxes/nova-kernel/src/linux-7.2.7`); `T` = the 615.71.09 tree (`../Leandro/vendor/open-gpu-kernel-modules`).
- `C` = `crates/vfio-user-nvgpu/guest/dmem-cap/`; `B` = `caraxes/runs/dmem-2026-09-29/`.

## Facts

### The dmem controller

- **Interface.** `dmem.max`, `dmem.min`, `dmem.low` take `<region> <bytes>|max` lines; `dmem.capacity` (root only) lists the regions; units are always bytes [K Documentation/admin-guide/cgroup-v2.rst:2866-2911].
  - `dmem.current` exists on the root too, although the text says it does not [K kernel/cgroup/dmem.c:849-858].
- **Where the files are.** Only in children of a cgroup with `+dmem` in `cgroup.subtree_control`; a controller can be enabled only where the parent enabled it [K cgroup-v2.rst:455-505]. Without that, every task's dmem css is an ancestor's and charges land there.
- **Who owns them.** A cgroup file is created with the fsuid of the task that caused it [K kernel/cgroup/cgroup.c:4446-4448]; a delegatee owns `cgroup.subtree_control` of its delegation root and distributes inside [K cgroup-v2.rst:540-570].
- **Who is charged.** `dmem_cgroup_try_charge` charges the calling task's cgroup, hierarchically (page_counter) [K dmem.c:103-106, 652-696].
- **A limit below the usage is a silent no-op.** `set_resource_max` drops `page_counter_set_max`'s `-EBUSY` [K dmem.c:160-163; mm/page_counter.c:197-227]. A fix ("atomically update irrespective of the current usage") was acked in April 2026 and is not in 7.2.7. Writers read the value back.
- **Kernels.** Since 6.14 (`CONFIG_CGROUP_DMEM`; T conftest.sh:5375-5388 cites commit b168ed4).
  - Ubuntu 24.04: `linux-generic-hwe-24.04` is **7.0.0-34** on 2026-09-29; 6.17.0-42 is still in noble-updates. Both have `CONFIG_CGROUP_DMEM=y`, `CONFIG_CGROUP_MISC=y`, gcc-13 (the `.config` of their header debs; sha256 checked against noble-updates `Packages.xz`, that against `InRelease`; the signature not checked).
  - The 6.8 GA kernel has no dmem.

### NVIDIA 615.71.09 memacct

- **Implementation choice.** dmem ("OS") when built against a dmem kernel and dmem is enabled at boot; else misc ("FALLBACK"); regkey `RmMemacctMode` can lower it [T kernel-open/nvidia/os-interface.c:2967-2978; src/nvidia/arch/nvalloc/unix/src/os.c:2147-2207].
- **Region.** `nvidia/%08X:%02X:%02X.0/vidmem`, size TOTAL_RAM_SIZE (`fb_length`), precharged with TOTAL − HEAP_FREE on the cgroup of the task that initialises the GPU [os.c:2209-2217; src/nvidia/src/kernel/mem_mgr/memacct.c:435-476; mem_mgr.c:826].
- **What is charged.** Only `NV01_MEMORY_LOCAL_USER` in `vidmemConstruct`, the requested bytes, not page-rounded [T video_mem.c:626-630]. RM-internal memory (GR context buffers, page tables, instance blocks) and UVM are not charged.
- **Which cgroup.** In dmem mode the calling task's (above); the client's creator cgroup only decides whether to charge at all (NULL: no charge) [memacct.c:170-245].
- **The fallback's limits** (`NV0000_CTRL_CMD_OS_UNIX_MEMACCT_SET_LIMITS` 0x3d0d, privileged) are refused in dmem mode with NOT_SUPPORTED [memacct.c:324-417]. Not used here: a private ioctl, not an upstream interface.
- **Versions.** memacct is in 610.43.02 and 615.71.09, not in 595.91.07 or 570.144: older guest drivers get no cap.
- **Cost per charge in a non-root cgroup.** A walk over all cgroups and a MEMACCT_SOFT_LIMIT_EXCEEDED event [memacct.c:103, 236-242; K dmem.c:254-352]. The control run carries the same cost.
- **Build for 7.0.** `nvidia-kernel-source-open 615.71.09-2ubuntu1` (the guest's package, sha256 against NVIDIA's `Packages.gz`) builds against the 7.0.0-34 headers on the host (nice 19, -j2, 2 min): conftest defines `NV_DMEM_CGROUP_PRESENT`, `nvidia.ko` imports the six `dmem_cgroup_*` symbols, vermagic `7.0.0-34-generic`; warnings only from objtool on the prebuilt `nv-kernel.o_binary` and the compiler mismatch (host gcc 16) [/mnt/vmstore/caraxes/dmem-2026-09-29/build.log].

### NVKMS, contiguity, userspace

- **NVKMS stays outside the cap.** Its kapi client is created at nvidia-drm probe by the modprobe task, with kernel privilege and no pid reference [T nvidia-drm-drv.c:727-756; client.c:120-134]; its RM calls run in the caller's thread [T nvidia-modeset-linux.c:946-957].
  - So NVKMS memory is uncharged once modprobe's pid is gone, or charged to gnome-shell/Xwayland in session.slice after a pid reuse; never to app.slice. The note's pid-reuse risk applies only to the misc fallback.
- **Bytes, not frames.** A limit guarantees bytes. Nothing guarantees five adjacent free 2 MiB frames for a 1080p SCANOUT buffer. The effective reserve also shrinks by apps' page rounding and by uncharged RM-internal growth after the cap is set.
- **NVIDIA's userspace reads dmem.** 615.71.09 `libnvidia-glcore`, `libnvidia-eglcore`, `libcuda`, `libnvidia-ml` contain `/proc/self/cgroup`, `/sys/fs/cgroup`, `dmem.max`, `dmem.min` (NVML also `dmem.current`) and `nvidia/%08X:%02X:%02X.0/vidmem %llu` (strings of the host's copies). Probably free memory and the Vulkan budget are clamped to the caller's limit (inference); whether ancestors count is open (test step 1).

### systemd

- No dmem support in 255 (Ubuntu 24.04) or 262 (host man pages); PR systemd/systemd#37079 (dmem.low/max directives) is a draft since February 2026.
- Its delegation doc: "Never write to any of the attributes of a cgroup systemd created for you."
- systemd writes `+`/`-` only for the controllers it knows (cpu, io, memory, pids), so a `+dmem` stays.
- `user@.service`: `Delegate=pids memory cpu`, `DelegateSubgroup=init.scope` (host 262).

## Design as built

- **Two halves, the kernel's delegation model:**
  - Root, in `user@.service`'s `ExecStartPre=-+` drop-in: `+dmem` in `/`, `user.slice`, `user-UID.slice` [C caraxes-dmem-delegate.conf].
  - The user, in the user unit `caraxes-dmem-cap.service` (session.slice, after `graphical-session.target` and Sunshine): `+dmem` in its delegated `user@UID.service`, then per NVIDIA region `app.slice/dmem.max` [C caraxes-dmem-cap.service].
- **Cap.** `dmem.max(app.slice) = dmem.current(app.slice) + free − R`, per region; current is read before free. Below current it stays at current with a warning. The value is read back.
  - Free: `nvidia-smi` memory.free (HEAP_FREE), run in session.slice, where no limit applies.
- **R = display reserve + session reserve.**
  - Display, automatic: per connected connector of the GPU, the largest mode it offers, `5 × S` each rounded up to 2 MiB, + 2 MiB. That is 52/82/162 MiB at 1080p/1440p/4K. The largest mode bounds any mode a compositor sets, so a mode change needs no recompute; the Caraxes EDID's largest mode is 1920x1080.
  - Session: `SESSION_RESERVE_MIB` (default 32) for what session.slice allocates after the cap, for example a stream's encoder buffers. Provisional: R's monitor saw +21 MiB at the stream start, not separated from Steam's start [caraxes/runs/night-2026-09-28/sottr-ca2559f5/guest-monitor.txt].
- **Sunshine in session.slice** (drop-in `Slice=session.slice`): its NVENC buffers must not fail when a game fills the cap (coordinator, 2026-09-29).
- **Knobs** in `/etc/caraxes/dmem-cap.conf`: `DISPLAY_RESERVE_MIB` −1 auto, 0 = no cap, N MiB; `SESSION_RESERVE_MIB`; `APP_SLICE`.
- **Logs.** The root half in `journalctl -u user@UID.service`; the user half in `journalctl --user -u caraxes-dmem-cap`; `caraxes-dmem-cap status` prints capacity, delegation, current and max per slice, NVML memory.
- **6.8 guests.** Both halves log "no dmem controller" and do nothing.
- **Tests.** `C/test.sh` runs the script against a fake cgroup and DRM tree and a fake nvidia-smi (23 checks: sizing, knobs, read-back, no dmem, no region).

### The deviation from systemd's rules, and its end

- Both halves write dmem entries into cgroups that systemd created, against its delegation doc. There is no other way to use dmem under systemd ≤ 262.
- Only dmem entries are written; systemd neither reads nor rewrites them.
- The switch once PR #37079 (or a successor) lands:
  - the root half becomes systemd's own delegation of dmem;
  - the user half's `dmem.max` becomes the new directive in an `app.slice` drop-in of the user manager (computed by a generator or a helper that writes the drop-in);
  - the script's measuring part stays.

## Test plan

Commands and order: [B/README.md](../../caraxes/runs/dmem-2026-09-29/README.md).

1. **Before the game** (`B/guest-dmem-check.sh`):
   - HWE kernel and the region in `dmem.capacity`;
   - both halves' log lines;
   - the cgroups of gnome-shell, Xwayland (session.slice), Sunshine (session.slice), Steam (app.slice);
   - NVML free and the Vulkan `heapBudget` outside and inside app.slice.
2. **SotTR 1080p with the cap:** `B/sottr-bench-dmem.sh` (DMEM_CAP=on). Pass:
   - 0 NVKMS failures, 0 Xids;
   - the results file written;
   - the host stream picture changing until the end;
   - the game in app.slice.
   - Five runs, since v1 failed 7 of 9 without its balloon.
3. **Control:** DMEM_CAP=off (same kernel, `dmem.max` = max). It must reproduce the refusal, as in R and twice on 2026-09-28.
4. **Record per run:**
   - app.slice current against its max, session.slice current, free VRAM at the peak (the effective reserve);
   - FPS against native 91.7 and v1.
5. **Calibration:** session.slice's growth after the cap (Sunshine's stream) sets `SESSION_RESERVE_MIB`; the free VRAM at the peak shows how much of R page rounding and uncharged RM memory take.

## Host side (later, optional; design only)

- **The host already runs dmem.** On 2026-09-29 the host (Arch, 7.2.7, 615.71.09) listed `nvidia/00000000:2D:00.0/vidmem 8589934592` in `/sys/fs/cgroup/dmem.capacity`, and the root `dmem.current` was 5528565280. Those were read-only cgroup reads; no NVIDIA module, parameter or register was touched.
  - The root's `subtree_control` has no dmem, so all charges sit in the root pool.
- **Design.** Each VM's device process (`vfio-user-nvgpu`, whose host RM client allocates the reservation, mirror channels and shadow tables) runs in its own scope, for example `systemd-run --user --scope --slice=caraxes.slice -u caraxes-<vm>`, with dmem delegated as in the guest.
  - The launcher sets the scope's `dmem.max` = profile reservation + a measured overhead before the device allocates.
- **Effect.** A device that leaks or misbehaves gets `RESOURCE_ACCOUNTING_HARD_LIMIT_EXCEEDED` from the host RM instead of eating the host desktop's VRAM. That is a kernel-enforced ceiling on top of the device's own reservation and floors (`CARAXES_HOST_VRAM_FLOOR_MIB`).
  - `dmem.min`/`low` would not protect the desktop: NVIDIA uses them only for the soft-limit notification, not for eviction.
- **Needed first.**
  - The per-VM overhead above the reservation, from the device log and `dmem.current` of the scope.
  - The launcher change.
  - The same systemd deviation on the host, with the same end.

## Status (2026-09-29, parked)

- **The HWE kernel works under the device.** 7.0.0-34 booted; DKMS built 615.71.09 for it (12 `dmem_cgroup_` strings in `nvidia.ko`) [B/prepare/prepare.txt].
  - Both halves ran: `/` → `user@1000.service` carry `+dmem`, and `app.slice/dmem.max` was set and read back [B/check-1.txt].
  - gnome-shell, Xwayland and Sunshine are in session.slice.
- **NVIDIA's userspace honours an ancestor's limit.**
  - `nvidia-smi` in a scope below app.slice reports total 593 = app.slice's `dmem.max` and free 573 [B/check-1.txt].
  - In the SotTR run the game stayed at 97 % of the cap (3461 of 3555 MiB) [B/cap-on-1/timeline.txt].
- **The cap works, R is too small** (SotTR 1080p, 4 GiB, cap 3555 MiB, R = 52 + 32 MiB) [B/cap-on-1/].
  - NVKMS refused at 648 s with free VRAM at 2 MiB, app.slice at 3461/3555, session.slice at 161; the game died.
  - After the cap was set, usage outside app.slice grew by about 175 MiB against R = 84:
    - session.slice +62 MiB (99 → 161, Sunshine's stream);
    - memory in no slice +113 MiB (RM-internal context buffers and page tables, NVENC sessions, page rounding), which was 153 MiB at the cap and about 266 MiB at the refusal.
  - The monitor's single samples mix three nvidia-smi calls about 1 s apart; during load bursts `vram − app` is skewed (even negative at 05:48:21).
- **Steam's shader-cache prompt.** Steam waited at "ProcessingShaderCache waiting for user response" with no visible window. The operator started the game directly with `systemd-run --user --scope --slice=app.slice` and `SteamAppId=750920`.
- **Next design step (not implemented).** A 1 Hz controller in the user unit: nvidia-smi `-lms 1000` as one long-lived process.
  - Each tick: `dmem.max = min(A_before, A_after) + (free − R) / (1 + ε)`, where A is app.slice's `dmem.current`, ε covers the RM-internal overhead of app allocations (about 2 % in cap-on-1), and R = display reserve + a burst margin.
  - Lower at once, raise with hysteresis, read back after every write, freeze at `dmem.current` when free < R.
  - HEAP_FREE counts frames still being scrubbed as free (their state stays FREE, `ATTRIB_SCRUBBING` is an attribute) [T src/nvidia/src/kernel/gpu/mem_mgr/phys_mem_allocator/phys_mem_allocator.c:1463; regmap.c:800-915]. So scrub-on-free adds no lag, and PMA waits for the scrubber before it fails [phys_mem_allocator.c:1057-1080].
- **Parked (the user, 2026-09-29).** First SotTR in a 6 GiB VM without a cap: if the game does not fit in 6 GiB, the problem is a leak, not the reserve. The operator runs it with copies of these scripts.

## 5 GiB without a cap (2026-09-29)

6 GiB does not fit beside the host desktop (it would leave the host 482 MiB; the device keeps 1 GiB), so the run used 5 GiB [B/fb5g-1/up.txt, ../sottr-6g refusal]. Scripts: `sottr-bench-6g.sh`, `desktop-b-dmem-6g.sh` (FB and floor as parameters; the game starts through Steam's scout `run.sh`, which gets past the shader-cache prompt and brings libopenal).
- **The game fills what it gets.** It took 94-97 % of the VRAM free at load in both sizes:
  - 4 GiB: app 3461 MiB; 5 GiB: app 4451 MiB at the peak [B/fb5g-1/guest-monitor.txt].
- **The same refusal, later.** NVKMS refused between 06:17:50 (free 99 MiB) and 06:18:06 (free 81 MiB); the stream froze while the game kept rendering (GPU 77-86 %), free fell to 8 MiB. The game was ended before the Xid 109 of the 720p run.
- **No leak.** After the game: vram 366 MiB, app 64, session 158, memory in no slice 144 MiB (200 before the game, 291 at the peak) [B/fb5g-1/after-game.txt].
  - The growth in no slice (~150 MiB) plus Sunshine's (~62 MiB) is bounded and returns.
- **Consequence:** more VRAM does not help; the cap does, with R covering that growth. Next: `DISPLAY_RESERVE_MIB=384` in /etc/caraxes/dmem-cap.conf at 4 GiB (the controller stays parked).
