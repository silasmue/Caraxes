**Judgment:** this is a close architectural relative of Leandro V1, with substantial Linux graphics sharing work. It is a useful independent design reference, not evidence that Caraxes V2's synthetic-PCI approach is unnecessary or slower. Its published game streaming is Linux/Proton; it is not Windows guest support. A direct performance ranking against either Leandro version is unsupported. In this session, our actual V1/V2 CUDA execution checks provide stronger compute evidence; their documented Wayland → encode → multi-guest results provide a stronger published end-to-end graphics story than our current V2 gates. Neither is an overall winner, and neither has validated hostile-tenant isolation.

## Architecture and useful implementation details

The library keeps VMM dependencies optional behind a `vhost-user` feature. Its shipped launcher starts a backend process separately from `nesbox`; thus prose saying host FDs are always inside the VMM is too broad. The planned per-process sandbox is still absent: process separation is not a jailer. See [device/Cargo.toml](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/Cargo.toml), [scripts/run-guest.sh](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/scripts/run-guest.sh#L45-L74), [isolate design only](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/isolate/README.md).

Guest compatibility is more complex than the README's ABI-unaware description. The C driver includes generated allocation-class sizes, rewrites selected V1 controls to V2, intercepts BUILD_VERSION locally and injects a UVM initialization flag. This is real ABI maintenance on both sides, even though the UMD is stock. See [guest ABI tables](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L49-L51), [local RM interception](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/nvgpu_rm_intercepts.h#L1-L38), [UVM flag rewrite](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2022-L2032).

Mapping the host usermode aperture directly is implemented, with a hardware-dependent mapping test. This permits a submission path without an ioctl round trip. Completion still costs event delivery. See [actual usermode aperture mapping test](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L3464-L3485).

The event pump uses edge-triggered epoll, duplicates watched FDs for lifetime safety, and has a one-millisecond sweep as a missed-notification fallback. It ignores guest kicks on the event queue rather than interpreting posted receive buffers as control requests. These are useful independently implementable correctness properties. The surrounding comments retain obsolete timer descriptions, so source behavior is the stronger reference. See [event pump](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/bin/vhost-user-nvgpu.rs#L192-L285), [event-queue direction guard](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/bin/vhost-user-nvgpu.rs#L514-L522).

DRM proxies use one host placement for node mmap, dma-buf mmap, kernel vmap and importer DMA addresses. Import accepts only a dma-buf from the same proxy device. This is a concrete ownership restriction, not arbitrary cross-device PRIME support. See [shared buffer mapping](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2544-L2770), [same-device import restriction](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2796-L2808).

## Strongest critical findings

1. **CODE: the advertised ABI allowlist is bypassed before version discovery.** `NoProfile` is allowed, and discovery occurs only following a guest-triggered CHECK_VERSION_STR. A guest can omit it. Versions older than the first profile likewise leave no table and warn instead of refusing. Existing tests explicitly preserve the pre-discovery behavior. See [NoProfile acceptance](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L1326-L1365), [version discovery](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L1222-L1242), [pre-discovery test](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L2731-L2736). This is a source-verified policy gap; no exploit was attempted.

2. **CODE: ABI checking is not an RM-command security policy.** It checks the NVIDIA escape namespace; RM class/control identifiers are counted and forwarded, while other ioctl namespaces lack the same table. See [namespace and class/control dispatch](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L1453-L1517). Therefore the default cannot be described as a full host-driver allowlist.

3. **INFERENCE: PRIME owner lifetime appears incomplete.** A proxy stores only numeric `owner_handle`; it does not retain the exporting DRM file. `nvgpu_drm_postclose` sends CLOSE unconditionally. An imported GEM object can remain referenced after that close, yet its later forwarding still uses the old owner. Source does not substantiate the prose promise that the compositor may safely outlive its exporter. This requires an export → import → exporter-close → importer-use regression; ordinary simultaneous presentation does not prove it. See [proxy object fields](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L636-L656), [proxy creation](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2840-L2865), [owner close](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L3527-L3545), [proxy final release](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2480-L2515).

4. **CODE: there is no demonstrated hostile-request resource envelope.** The standalone backend allocates buffers using guest descriptor lengths before a cumulative request cap; only response capacity is clamped. This exposes a memory-exhaustion surface. The reviewed tree contains no runtime seccomp/uid-drop jailer. See [descriptor allocation before validation](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/bin/vhost-user-nvgpu.rs#L406-L430), [isolate design only](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/isolate/README.md). Treat this as an attack-surface finding, not a demonstrated host compromise.

5. **CODE: ABI compatibility has deliberate approximation.** Profiles use the greatest known version <= host version, including indefinitely newer releases. The shipped generator parses gVisor Go ABI declarations and computes layout; it is not the README's described per-field compilation of NVIDIA C headers. Hardware fixtures independently check some sizes, which is useful, but do not validate every class/control. See [profile selection](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/gen/src/versions/mod.rs#L56-L80), [generator inputs](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/gen/nvabi_gen.py#L1-L18), [Go layout parser](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/gen/nvabi_sizes.py#L1-L15), [fixture methodology](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/gen/README.md#L54-L73).

6. **CODE: success can be synthesized.** SYS_PARAMS EBUSY handling may return a zeroed success reply. Generic enumeration success must therefore not be treated as proof every host operation succeeded. See [SYS_PARAMS fallback](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L1985-L2005).

## Host-memory import, quotas and lifetime comparison

No equivalent of V1's guest-GPA-run aliasing and host registration was found in the external tree. A generated class-size entry for OS-descriptor memory does not implement pointer pinning or translation. Its RM_ALLOC_MEMORY path translates a file descriptor, while its generic PRIME import accepts only buffers already owned by its proxy. This is an observed implementation limit; a complete unsupported-CUDA-operation list was not established. [FD translation](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/nvidia.rs#L2111-L2140), [PRIME restriction](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/driver/virtio_gpu_nv.c#L2796-L2808).

The external 1 GiB shared window is partitioned into 32 MiB uncached, 768 MiB write-combining and 224 MiB write-back zones. That is a CPU mapping-address-space bound, not a VRAM quota. There is real free-extent coalescing and backing restoration, but no per-VM VRAM accounting ledger was found. [Window zones](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/shm.rs#L134-L176), [free ordering](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/device/src/shm.rs#L319-L348).

The V1 integration baseline already contains distinct machinery: `host_pool.rs:266+` validates and aliases guest GPA runs; `:485-513` registers those host virtual addresses as OS descriptors with a same-process duplication grant. `PinBudget::from_env` defaults to 1 GiB per VM and reserves with checked aggregate accounting (`:56-95`). `vram.rs:616+` implements a per-VM ledger; `Books::settle/free_object/close_token/Drop` release charges on failed allocation, object destruction, descriptor closure or session teardown (`:956-1026`). These features are configuration-dependent: `Policy::Off` is the default (`:55-69`), and the overhead allowance explicitly does not bound all RM allocations (`:50-52`). This establishes implemented control points, not a hostile-tenant security proof.

**New V1 function-27 path, distinguished from that legacy path:** the parent task has since tested commit `0e23ed72246b4e84546d8287a1075db5ed27e09f` in `/mnt/vmstore/caraxes/leandro-v1-hostptr-import` (current HEAD `1cf19cd030d83d76767df8a48f9ce0a621411a29`). It implements bounded VID_HEAP virtual-address imports and explicitly refuses DUP, SHARE, UVM external-map and Unix-FD-export aliases for those imported handles. It may release backing after acknowledged FREE/CLOSE under that narrower policy; legacy 0x71 imports remain retained because aliases are possible. Source: that worktree's `session.rs:1368+`, `host_pool.rs:702+`, and commit's `docs/SECURITY.md` update. Parent-reported hardware validation: 32 cycles plus a GPU 4 KiB copy; opened/closed descriptors 246/246, pinned bytes returned to zero. I did not rerun those tests. This is stronger specific import/lifetime evidence than anything found in the external repository, while unrecognized alias operations remain a stated limitation.

Reported four-guest aggregate: 103.69 fps versus 102.9 for one guest. A2000 / 615.71.09 game streaming has no native comparison or recorded frame pacing. Public evidence is summary tables; machine harnesses remain private and benchmark/test revisions are not pinned. One stream paragraph gives p99 26.03 ms and max 26.16 ms; another says zero gaps above 25 ms and p99 18.0 ms. Those cannot describe one run without further qualification. See [BENCHMARKS.md](https://github.com/nestrilabs/virtio-nvgpu/blob/9c28b1988e0d02c6012c7eb3e3f878890b944a58/BENCHMARKS.md).

The README's Venus comparison is explicitly unmeasured. Neither its 90–97% column nor a cross-project victory follows from these experiments. Varying fragment-shader cost at fixed image size also does not reproduce a game's allocation churn, CPU scheduling, shader compilation, presentation or long-session behavior. These are limits of generalization, not evidence that the measurements were fabricated.

## Actionable lessons for our own implementation

- **V1:** independently test exporter-close/importer-use and every descriptor-containing NVKMS request; numeric handle rewriting alone is insufficient. Check these against our existing session/PRIME lifetime machinery rather than assuming they are absent.
- **V1/V2:** measure idle CPU and host/guest CPU together with throughput. Exercise event starvation, duplicate readiness, teardown while watched, and restart; a busy-spin path can look faster.
- **V1:** initialize ABI policy from trusted host discovery before accepting guest traffic; fail closed for unknown versions/commands except the minimal explicit discovery path. This is a review criterion, not imported code.
- **V2:** direct mapped submission does not settle the tradeoff against validated channel mirroring. Our ioeventfd and BAR1 paths should be evaluated with their validation/translation costs and supported modes intact.
- **Evidence:** add our own render/capture/encode checks and native baselines with pinned binaries, raw logs, CPU accounting and long repeated teardown cycles. Do not reuse their benchmark programs or treat their relative numbers as ours.
- **Windows:** this repository supplies no direct solution for the failing stock Windows KMD initialization. Its Linux proxy sidesteps that interface entirely.
