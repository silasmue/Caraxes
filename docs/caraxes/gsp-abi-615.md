# The GSP ABI baseline: 615.71.09

Decision D20 ([README.md](README.md)): **615.71.09 is the recorded GSP ABI baseline of this
project; later driver versions are handled as diffed deltas against `caraxes/abi/`.** The
operator's reason: from 615 on NVIDIA marks the GSP transport and boot structures
`NV_ABI_STABLE`, so the boundary the device emulates should change only a little from here,
like a stable ABI with incremental hardware additions. This document says what the baseline
is, where NVIDIA itself draws the stable line, what the tree calls unstable, the numbers of the
baseline, the 610-to-615 delta as the worked example, and the workflow for the next driver.

Paths of the driver tree are relative to its root (615 unless marked 610). Device paths are
`crates/vfio-user-nvgpu/...`.

## 1. What is recorded

| Path | Contents |
|---|---|
| `caraxes/abi/gsp-615.71.09/` | the baseline snapshot, generated, not typed |
| `caraxes/abi/gsp-610.57.04/` | the same for 610.57.04, the first delta's base |
| `caraxes/abi/delta-610.57.04-615.71.09.md` | the delta report of the two (`gsp-abi.py diff --out`) |
| [gsp-abi-615-tables.md](gsp-abi-615-tables.md) | the baseline as human-readable tables (`gsp-abi.py render`) |
| `caraxes/tools/gsp-abi.py` | `snapshot`, `diff`, `render` |
| `caraxes/abi/gsp-615.71.09/transport.tsv` | not part of the snapshot: the transport class of every routed control, generated by `caraxes/tools/gsp-transport.py` from the snapshot, the 615 tree and the profiles ([gsp-transport-classes.md](gsp-transport-classes.md)) |

A snapshot directory holds these files, each a TSV with an SPDX comment header, one header row
and one row per item, sorted, so that `git diff` of two snapshots is readable too:

| File | One row per | Columns |
|---|---|---|
| `controls.tsv` | exported control id (1397 in 615, of which 16 are controls the kernel RM sends to GSP without an export entry) | id, name, NVOC classes, params struct, size, layout hash, route (`gsp` or `kernel`), why it is routed, RMCTRL flags, privilege, category A to E, the device's answer (host-forwarded, synthesized, guest-derived, echo, refused, unhandled), the device rule that answers, source line |
| `rpc.tsv` | RPC function of `rpc_global_enums.h` | number, name, newest payload struct, size, layout hash, all struct versions, sent by a GSP client, device |
| `events.tsv` | RPC event | number, name, payload struct, size, layout hash, dispatched by the CPU side, sent by the device |
| `classes.tsv` | `RS_ENTRY` of `resource_list.h` | class, id, internal class, route (`RPC_TO_ALL`, `RPC_TO_PHYS_RM`, constructor RPC, kernel), reaches GSP, alloc params struct, size, layout hash, in the TU106 class database, device |
| `boot.tsv` | `NV_ABI_STABLE` type, and transport or boot struct the device implements | name, kind, size, layout hash, version constants, stable-tagged, used by the device, definition file:line |
| `layouts.tsv` | field of a laid-out struct | struct, field path, offset, size, origin (`gsp-abi-sizes.sh` for the boot structs, `ctrl-layouts.py` for the control structs the device lays out) |
| `constants.tsv` | derived transport constant, version constant, GMCAPI key | name, value, origin (the GMCAPI header, `*_unstable.h` for unstable keys) |
| `enums.tsv` | enumerator of an `NV_ABI_STABLE` enum | enum, enumerator, value |
| `bitfields.tsv` | DRF bit range of a control or GMCAPI header | name, bits, file:line |
| `MANIFEST` | | driver version, sha256 of `version.mk`, repository commit, generator command line, compilers, rows and sha256 per file |

**How it is measured.** The inventory (controls, routing, RPC functions, events, classes and
the device's answer) is `caraxes/tools/gsp-surface.py`, imported by `gsp-abi.py`, with its
method ([gsp-surface.md](gsp-surface.md) §1). Every size is `sizeof` from the compiler: the
control and class parameter structs against all SDK headers of the tree
(`src/common/sdk/nvidia/inc/{nvos.h,ctrl,class,alloc}`, `cc -std=gnu11 -DNV_LINUX`), the RPC,
event, transport and boot structs with the minimal RM flag set of
`caraxes/tools/gsp-abi-sizes.sh --print-flags`. The layout hash is a hash of clang's record
layout (`-fdump-record-layouts`) with every offset, type and field name, including the element
records of arrays, so a field inserted or moved at the same size changes it. Field offsets
come from the two existing generators: `gsp-abi-sizes.sh` (boot and transport structs, and the
derived constants such as `maxRpcSize`) and `ctrl-layouts.py` (the control structs
`chips/*/controls.toml` names and the D structs with a model or a layout change). The
driver-side columns depend only on the tree: a second snapshot of the same tree, from another
directory, is byte-identical. The device columns are read from the crate at the snapshot's
commit.

```
python3 caraxes/tools/gsp-abi.py snapshot --ogkm <615.71.09 tree> --out caraxes/abi/gsp-615.71.09 \
    --tables docs/caraxes/gsp-abi-615-tables.md
python3 caraxes/tools/gsp-abi.py diff caraxes/abi/gsp-610.57.04 caraxes/abi/gsp-615.71.09 \
    --out caraxes/abi/delta-610.57.04-615.71.09.md
python3 caraxes/tools/gsp-abi.py diff --strict caraxes/abi/gsp-615.71.09 <615.71.09 tree>   # drift
python3 caraxes/tools/gsp-abi.py render caraxes/abi/gsp-615.71.09 --check docs/caraxes/gsp-abi-615-tables.md
```

`diff` takes snapshot directories or driver trees (a tree is snapshotted into a temporary
directory first). Its exit code is 1 when a struct the device implements changed size or field
offsets (a control it answers other than by refusal, an RPC function or event it handles, a
class it models or acknowledges, a boot type it uses, a changed value of a stable enumerator or
a promoted GMCAPI key), and with `--strict` on any driver-side difference; changes of the
device's own answers are listed apart and never fail.

## 2. What NVIDIA marks stable, and where

The tag is defined in `src/common/sdk/nvidia/inc/nvtypes.h:521-533`: "This tag can be applied
to a type to mark it as ABI-stable and block most changes to the internal layout. In all
driver builds, this tag is a NOP and is there for human benefit only. However, static checker
tools may support the custom attribute and use it to verify no changes across releases." It
becomes `__attribute__((nv_abi_stable))` only under `NV_ABI_STABLE_CHECKED_BUILD`; the same
text is in `kernel-open/common/inc/nvtypes.h:537-540`. 610.57.04 has no such tag. Every use in
the 615 tree (`boot.tsv`, column `stable`):

| Type | Where | Size | On TU106 |
|---|---|---:|---|
| `msgqTxHeader` | `src/nvidia/inc/libraries/msgq/msgq_priv.h:82` | 32 | yes, both queue headers |
| `GSP_MSG_QUEUE_ELEMENT` | `src/nvidia/inc/kernel/gpu/gsp/message_queue_priv.h:90` | 40 (24 without the CC tag) | yes, every element |
| `MESSAGE_QUEUE_INIT_ARGUMENTS` | `src/nvidia/inc/kernel/gpu/gsp/gsp_init_args.h:33` | 64 | yes, RMARGS |
| `GSP_SR_INIT_ARGUMENTS` | `gsp_init_args.h:50` | 16 | yes, RMARGS |
| `GSP_ARGUMENTS_CACHED` | `gsp_init_args.h:60` | 184 | yes, RMARGS |
| `GMCAPI_HEADER` | `src/nvidia/interface/gmcapi/gmcapi_base.h:27` | 40 | yes, `GSP_INIT`, `GSP_SUSPEND`, `GSP_RESUME_DONE` |
| enums `GMCAPI_HEADER_COMMAND_FLAGS`, `GMCAPI_FLAGS`, `GMCAPI_COMMANDS` | `gmcapi_base.h:56, 63, 74` | | yes |
| enum `NVGMC_ENGINE_TYPE` | `src/nvidia/interface/gmcapi/gmcapi_engine_types.h:29` | | yes, the `ENGINE_MASK` key |
| enum `GMCAPI_VGPU_PLUGIN_EVENT` | `src/nvidia/interface/gmcapi/gmcapi_vgpu.h:194` | | no (vGPU host) |
| `GSP_FMC_INIT_PARAMS`, `GSP_ACR_BOOT_GSP_RM_PARAMS`, `GSP_RM_PARAMS`, `GSP_SPDM_PARAMS`, `GSP_RM_MEM_PARAMS`, `GSP_FMC_BOOT_PARAMS` | `src/nvidia/arch/nvalloc/common/inc/gsp/gspifpub.h:50, 63, 90, 105, 118, 127` | 8, 32, 16, 16, 8, 256 | no (GSP-FMC boot, Hopper and later) |

That is 12 structs and 5 enums. The rules NVIDIA writes next to them:

- Stable structs grow into reserved space: "If extending any of the NV_ABI_STABLE sub-structs,
  make sure to remove the corresponding reserved fields from the parent struct"
  (`gspifpub.h:33-34`). `GSP_ARGUMENTS_CACHED` and `MESSAGE_QUEUE_INIT_ARGUMENTS` carry such
  reserved words ([gsp-transport-615.md](gsp-transport-615.md) §6).
- The queue header versions itself: "Major versions get increased with incompatible changes",
  "Minor versions are compatible" (`msgq_priv.h:31-34`; major 2, minor 0 in 615,
  `constants.tsv`).
- GMCAPI ids up to 0xFFFF are reserved, so a GMCAPI command never collides with an RPC
  function number (`gmcapi_base.h:76-80`); the commands themselves come from the X-macro table
  `gmcapi_table.h` pasted into the stable enum (`gmcapi_base.h:82-85`; 22 commands in 615,
  `enums.tsv`).

Stable by construction but not tagged, although the device reads them on every boot (in
`boot.tsv` with `stable no`): `rpc_message_header_v` and the RPC payloads the device answers,
`GspFwWprMeta` (`src/nvidia/arch/nvalloc/common/inc/gsp/gsp_fw_wpr_meta.h:210`),
`LibosMemoryRegionInitArgument`, `GspStaticConfigInfo` and `GspSystemInfo` (internal in 615,
sent as NVKV words), `GmcApiGspSuspendParams` and `GmcApiGspResumeDoneParams`
(`gmcapi_gsp.h:39, 63`), and the NVKV encoding.

## 3. What the tree calls unstable

- **The RM RPC layer is an opt-in "unstable interface".** The kernel must opt in to "unstable
  interfaces to GSP" with one bit for RPCs and one for events
  (`NVGMC_SI_UNSTABLE_INTERFACE_SUPPORT` 0x1110, bits `_RPC` 0:0 and `_EVENTS` 1:1,
  `src/nvidia/interface/gmcapi/gmcapi_system_info.h:200-203`), and the 615 kernel sets both
  (`src/nvidia/src/kernel/gpu/gsp/kernel_gsp.c:5203-5206`). The device honours the opt-in
  ([gsp-plan/boot-exchange.md](gsp-plan/boot-exchange.md) B7). Everything carried by that layer
  is outside the stable promise: `GSP_RM_CONTROL`, `GSP_RM_ALLOC` and every control and alloc
  parameter layout, the events, and the RPC function numbers.
- **The internal handles.** "These are only valid if using RMAPI RPCs with GSP and should be
  avoided/ignored as any RPCs that rely on them are considered ABI unstable"
  (`gmcapi_gsp_config.h:74-78`, `NVGMC_SC_INTERNAL_CLIENT_HANDLE` and the device and subdevice
  handles).
- **Unpromoted NVKV keys.** "Keys that are still under development (or can change depending on
  build configuration) live in this file until they get promoted"
  (`gmcapi_system_info_unstable.h:27-28`, `gmcapi_gsp_config_unstable.h:31-32`); in 615 that is
  `NVGMC_SI_CL_FLAGS` 0x1033 (`constants.tsv`, origin `gmcapi_system_info_unstable.h`).
- **Queue encryption.** "GSP Message Queue encryption is currently *NOT* ABI stable"
  (`message_queue_priv.h:45`); `GSP_MSG_QUEUE_ENCRYPTION_TAG` changed from 40 to 16 bytes
  between 610 and 615.
- **The version lock stays.** The kernel accepts only a GSP-RM image whose `.fwversion` equals
  its own version string (`_kgspFwContainerVerifyVersion`, `kernel_gsp.c:6401`, called at
  `:4190`). NVIDIA never mixes versions; "stable" is a promise about the boundary, not a
  compatibility mode, and the device keeps serving one guest ABI per build (D14).

So the baseline has two layers with different expectations. The stable layer (transport, boot
arguments, GMCAPI header and commands, promoted NVKV keys) should not change at all. The
unstable layer (every control, alloc, RPC and event layout, the internal handles) will change
per version, and the snapshot is what makes that change visible and cheap.

controls the device calls on the host. And flag-word changes never fail: a bit range belongs
to a define, not to a struct the diff can tie to a handler. Both are what step 5 of the
workflow is for.

## 6. The workflow for the next driver version

For a driver `N` (a new tree `<tree-N>`, for example 620.x):

1. **Snapshot.** `python3 caraxes/tools/gsp-abi.py snapshot --ogkm <tree-N> --out
   caraxes/abi/gsp-N/`. Commit it on its own, generated at a clean commit (the MANIFEST
   records the commit and whether `crates/` or `caraxes/tools/` had uncommitted changes).
2. **Diff against the baseline.** `python3 caraxes/tools/gsp-abi.py diff caraxes/abi/gsp-615.71.09
   caraxes/abi/gsp-N --out caraxes/abi/delta-615.71.09-N.md`. Read the summary, then the
   section "Changes to what the device implements"; exit 1 means at least one of those.
3. **Classify every change.** The stable layer (section 7) first: any change there is a
   baseline break and stops the workflow for a decision. Then per group: added controls,
   classes and RPCs get a category (the generators do that), resized and relaid-out structs
   the device answers get a new per-version layout, reused ids get a per-version meaning
   (`ver::Id0A36` is the pattern), routing and privilege changes decide whether an arm is dead
   or a host forward becomes possible. Redo the sender survey for RPC functions whose senders
   changed (`GSP_CLIENT_SENDS_615`, `gsp-surface.py`).
4. **Regenerate the per-version tables** into `crates/vfio-user-nvgpu/src/ver/vN/` with the
   three generators, after the version's `nvrm-sys` bindings exist (`tools/build.sh vendor-abi
   N`, `cargo run -p xtask -- abi`, a `[versions."N"]` entry in `crates/nvrm-sys/abi.toml`):
   `caraxes/tools/gsp-tables.py --ogkm <tree-N>` (`surface.rs`: routed controls, E families,
   inventory counts), `caraxes/tools/ctrl-layouts.py --ogkm <tree-N>` (`ctrl_layouts.rs`),
   `caraxes/tools/gsp-dtable.py --ogkm <tree-N>` (`dmodel.rs`). The version module `ver/vN.rs`
   builds on the previous one and overrides what the diff says moved (as `ver/v615.rs` does on
   `ver/v610.rs`, with the `versioned_layouts_are_overridden_where_they_differ` test).
5. **The host side.** If the host driver moves to `N` too, add a row per changed host call to
   `crates/vfio-user-nvgpu/src/hostabi.rs`: every kernel-side control, allocation and flag word
   the device sends to the host whose layout the diff shows changed (the TSG allocation,
   `GPU_GET_PES_INFO`, `GR_GET_GLOBAL_SM_ORDER`, `FB_FLUSH_GPU_CACHE` flags, the GSS legacy
   sizes from an `nvidia-smi -q` trace), and the exact version string for its selection.
6. **Run the gates**, pure emulation first, then with the host: `tools/check.sh`, the
   device's unit tests, and the guest gates of [testing.md](testing.md) with a guest image of
   version `N`.
7. **Record.** A delta section in this document (or its successor for `N`), the plans'
   status lines, and, if `N` becomes the new baseline, a decision row replacing D20 and a new
   drift check target.

## 7. What is expected to change, and what would break the baseline

**Expected, and handled by the workflow:**

- New controls, mostly INTERNAL ones for new features and new silicon, and new families for
  new chips (of the 21 new ids of 615, 15 are routed: 7 NVLink, 4 vGPU-manager, two display
  controls, one perf control and `NV0090_CTRL_CMD_PROGRAM_SYSMEM_PROMOTE`). They arrive unhandled, get a
  category, and on TU106 mostly land in an absent E family.
- Size changes of versioned parameter structs, by an appended field, a larger fixed array or
  an inserted field (28 controls of 610 to 615); the answer's layout comes from the version's
  generated module.
- New RPC function and event numbers appended at the end of the enum, new struct versions
  (`_v2F_xx`) of existing functions, new classes for new engines.
- Id reuse inside a control interface (0x20800A36, the NVLink shift): rare, and the reason the
  diff compares names per id.
- New NVKV keys and GMCAPI commands in the category ranges, and keys promoted from the
  `*_unstable.h` files.

**Would break the baseline assumption** (stop and decide, not a routine delta):

- a size, field offset or version constant change in any `NV_ABI_STABLE` struct
  (`boot.tsv` `stable yes`, `layouts.tsv`), or a changed value of a stable enumerator;
- the message queue element framing: `GSP_MSG_QUEUE_ELEMENT`, `MCTP_MAGIC`, the NVDM types
  0x25 and 0x26, `queueElementHdrSize`, `maxRpcSize`, or a `MSGQ_VERSION_MAJOR` other than 2;
- the boot arguments: `GSP_ARGUMENTS_CACHED` (magic, size, the `MESSAGE_QUEUE_INIT_ARGUMENTS`
  inside it), `GSP_SR_INIT_ARGUMENTS`, `GspFwWprMeta`, the RMARGS libos region;
- the GMCAPI header or the value of an existing GMCAPI command or promoted NVKV key;
- the unstable-interface opt-in itself changing meaning (a third bit the kernel sets that the
  device does not know, or the RPC layer declared stable, which would move controls into the
  stable layer).

## 8. The drift check

`tools/check.sh` step `gsp-abi` (function `gsp_abi_baseline`):

1. `gsp-abi.py render caraxes/abi/gsp-615.71.09 --check docs/caraxes/gsp-abi-615-tables.md`:
   the tables document must be exactly the rendering of the snapshot, so the human table never
   lags the TSVs.
2. When a 615.71.09 tree is found (`$CARAXES_OGKM_615`, else the Leandro checkout beside this
   repository, `<git common dir>/../../Leandro/vendor/open-gpu-kernel-modules`, else
   `/mnt/vmstore/caraxes/ogkm-615.71.09`; its `version.mk` must say 615.71.09) and `cc` and
   `clang` are installed: `gsp-abi.py diff --strict caraxes/abi/gsp-615.71.09 <tree>`, a fresh
   snapshot of the tree compared on the driver side. Any difference fails. Without a tree the
   step passes with a note that the drift half was skipped.

Changed device answers are printed in their own section and do not fail the step: the crate
grows answers daily, and the snapshot records them when it is regenerated (workflow step 1).
Result on 2026-09-25 against the Leandro checkout's tree: 0 driver-side changes, 0 device-side
changes, the tables document up to date.

## 9. Limits

- The categories A to E and the device's provenance are the heuristics of `gsp-surface.py`
  ([gsp-surface.md](gsp-surface.md) §1); they are recorded as they are, so a heuristic
  improvement shows as a device-side change.
- Controls compiled only into other build profiles (Windows) are not in the export tables of
  this tree and not in the snapshot.
- 62 exported controls have no parameters (size 0); every named parameter struct was measured.
- The layout hash is a signal, not a description: a hash change at equal size says "look",
  and the field view exists only for the structs `gsp-abi-sizes.sh` and `ctrl-layouts.py` lay
  out. Adding a struct there (for example the SM-order entry) adds its fields to the next
  snapshot.
